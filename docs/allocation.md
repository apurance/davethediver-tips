# 经营分配

入口：侧边栏「经营分配」，路由 `/allocation`。

日常与八类派对全部展开陈列，每个区域都能分别为主店和分店配置多道菜及供应份数。新方案的派对默认不沿用日常，空菜单表示该店当晚不供应；需要继承时手动开启“沿用日常”。顶部的菜单导航只跳转位置，不隐藏其他区域。每个区域可点击“查看单晚用料”，底部默认展示全方案的长期日均需求。

顶部下拉框切换经营方案，支持新建空白方案、复制当前方案、重命名和删除。每个方案独立保存日常菜单、派对菜单和周期设置；重置仅影响当前方案，至少保留一个方案。方案仍存储在当前浏览器的 `blue-hole-allocation-v1`，内容升级为版本 2 的方案列表。旧版单方案自动迁移为「方案 1」，保留原菜单、周期及已保存的沿用设置。重置与删除前有二次确认。

## 用料计算

- 供应份数是希望售出的成品份数，每批份数固定读取菜谱满级值，不再提供输入；每道菜以一行展示菜名、供应份数、满级制作批次和删除按钮。旧方案中的自定义每批份数不再参与计算。
- 每店、每道菜的制作批次 = `ceil(供应份数 / 每批份数)`；同店重复的菜先合并，主店和分店分别取整。
- 材料需求 = 制作批次 × 配方数量。没有配方、配方数量或每批份数时显示不完整提示，不能当成零成本。
- 不计员工额外出餐、强化菜谱消耗、库存扣减或繁殖随机性。
- `普通日 = 规划天数 − 各派对次数之和`。派对菜单替换当晚日常，继承菜单按该店日常计算。
- `周期材料 = 普通日 × 日常材料 + Σ(派对次数 × 对应派对材料)`。
- `日均材料 = 周期材料 / 规划天数`。在完整批次计算之后平均，不对每日平均值向上取整。周期无效时阻止折算，保留当前单晚备货。

鱼类需求按本地栖息区域与夜行标签归组，钟乳石洞和遇难船归中层池，冰河洞穴归冰河池，DLC 或不明确区域另列。该映射不是逐鱼核实的可养殖白名单。金枪鱼部位、鲨鱼头、海马等特殊材料保留材料 ID，显示对应鱼种，不套用整鱼产肉率。鱼数使用图鉴二星或三星产肉量作为参考；这是需要出货的数量估算，不是种鱼保留量或稳定繁殖量。

## 派对周期研究（2026-11-06）

- [Steam 玩家讨论：Do Party events repeat?](https://steamcommunity.com/app/1868140/discussions/0/3806156942409507760/)：2023-08-08 玩家称每五天一次、首轮后随机。该讨论使用旧版七类派对口径，不能用它证明当前八类等概率或固定轮回。
- [Steam 玩家讨论：Do we run out of events/VIPs?](https://steamcommunity.com/app/1868140/discussions/0/7318962605503582457/)：同样描述五天间隔和随机顺序。仍是社区经验，并非当前版本官方日程或概率表。
- [鱼池区域参考](https://dave-the-diver.fandom.com/wiki/Fish_Farm)：七个本体池区包含独立夜潜池。页面检索结果可读，全文抓取受限。
- [用户指定贴吧攻略](https://tieba.baidu.com/p/11013912740?fr=frs)：检索工具不可访问，直接 HTTP 请求（含移动页）返回 403；未读取到正文，未将其作为公式依据。

因此默认 **40 天、八类派对各一次**仅是可调整的预算假设，相当于假设每五天一场且各类型等频。它不意味着 40 天内必然各出现一次，也不预测下一场派对。玩家可按存档实际记录修改天数与各类次数。长期日均不能保证某场随机派对前的库存充足，应同时查看该派对的单晚备货。
